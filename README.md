# 图片查重 · ImageScout

一个**零第三方依赖**的本地图片查重工具（Windows）。纯 Python 标准库 + Tkinter + ctypes，
不装 Pillow、不装 numpy、不联网也能跑。

它要解决的问题不只是「找出一模一样的图」，而是：

1. **同一张图的不同裁剪**也算相似（`full` / 方形 / 16:9 / 3:4 / 裁边 / 偏心 / 缩半）；
2. **同场景不同构图**（连着拍好几张、换个角度）也尽量找出来，但单独标成「疑似」；
3. 对比时**两张图并排、可滚轮放大**，把**两图信息按同一组字段左右并排**，
   给一排快捷操作，**看完了能直接把不想要的删掉**（删到隔离夹，不是真删）。

![界面](screenshot.png)

并排对比态（左：相似分组列表 + 本组成员，右：两图并排 + 两列信息 + 快捷操作）。

切到「全部图片」视图，质量差的图会被排到前面并挂上徽章 ——
分辨率不够的写「低清」，尺寸够大但压缩完只剩几 KB 的写「体积小」：

## 怎么跑

双击 **`启动.bat`**（会自动找带 Tkinter 的 Python），或者：

```bat
python image_scout.py                :: 打开后自己添加文件夹
python image_scout.py D:\某目录       :: 直接把目录作为扫描源
python image_scout.py a.jpg b.png     :: 也可以直接给图片
```

> ⚠️ 必须用**带 Tkinter 的 Python**。托管运行时（`C:\Users\WQ\.workbuddy\binaries\python\...`）
> 没带 Tk，本机可用的是 `D:\python\python-3.13.5\python.exe`，`启动.bat` 里已经写好了回退路径。

### 打包成单文件 exe

`ImageScout.exe`（约 12.8 MB）已经打好了，就在仓库根目录 —— 双击 `启动.bat`
会**优先用它**（`启动.bat` 的逻辑：同目录有 exe 就跑 exe，没有才找 Python）。

自己重新打包（改完代码后）：

```bash
# 隔离环境装 PyInstaller（只需一次，.build-venv 留着下次用）
"D:/python/python-3.13.5/python.exe" -m venv .build-venv
".build-venv/Scripts/python.exe" -m pip install --upgrade pip pyinstaller

# 打包：onefile + 无黑框 + 图标内嵌
# ⚠️ 不带 --clean（构建缓存留着，Analysis 只在源码变化时重建，快得多）
".build-venv/Scripts/pyinstaller.exe" --noconfirm --onefile --windowed \
    --name "ImageScout" --icon "app.ico" --add-data "app.ico;." \
    --distpath "dist" --workpath "build" --specpath "." image_scout.py

# 出包后把 exe 拷到根目录（启动.bat 只认根目录这份），构建缓存可删
cp dist/ImageScout.exe . && rm -rf build dist
```

- 各功能模块（`scan` / `uikit` / `niqe` …）PyInstaller 会**自动分析 import** 打进去，
  不需要 `--add-data`；只有 `app.ico` 是运行时数据，要手动带一份。
- `image_scout.py` 里的 `resource_path()` 会在打包后从解包目录（`sys._MEIPASS`）找
  `app.ico` 给窗口挂图标 —— 源码跑则直接用同目录的。
- **打包完必须启动一次截图验收**：`python verify_exe.py`（启动根目录的 exe、
  按窗口类名 `TkTopLevel` 找窗 —— onefile 是双进程，不能按 pid 找 —— 抓成 `shot-exe.png`）。
- 打包工具链的其他坑见 `verify_exe.py` 头注释；图标缓存不刷新是 Windows 的事，跟 exe 无关。

几个刻意为之的地方：

- **选中一组就自动对比**，用的是「代表图 ↔ 与它最像的那张」。想换另一张比，
  在左下角点一下就行，不点任何按钮。
- **两图信息放在同一行同一字段上**（分辨率 / 质量 / 清晰度 / 网格 / 匹配区域…），
  竖着扫一眼就能看出差异 —— 不是「选中哪张才显示哪张的信息」。
  信息区压成紧凑几行，**高度全让给图片**。
- **预览尽可能大**：按格子的实际尺寸向系统解码器要像素（带 `SIIGBF_SCALEUP`，
  所以小图也会被放大到填满格子）。**滚轮缩放会重新按放大后的尺寸要一次像素**，
  不是把已解码的小图硬拉（Tk 的 `zoom` 是最近邻，拉两倍就是马赛克）。
  放大后按住鼠标可拖动看局部，「重置缩放」回到适应窗口。
- **滚轮只缩放「鼠标底下那一侧」** —— 因为对比时经常要「左图看整体、右图抠局部」，
  两边一起缩放就没法这么用了。实现上不能拿鼠标坐标去猜是哪一侧（单图模式下
  左画布会横跨整行，猜出来的列号是错的），而是在绑事件时用闭包把列号带进去。
  缩放/平移状态都是**每侧一份**（`zoom = [左, 右]`），「重置缩放」才两侧一起归位。
- **双击图片 = 用系统看图器打开**（原来那两个「打开 A/B」按钮已删掉）。
- **匹配区域的红框已经去掉了**（挡着看图）。要看对应部位就点「只看匹配区域」，
  它会把两侧匹配的那块裁出来并排 —— 一眼看出「就是同一张，只是裁剪比例不同」。
  这时下面的标题会老实说明「仅匹配区 236 × 233 · 占本图 26%」，
  而不是拿整图分辨率说事（以前写着「560 × 380 · 显示 107%」，看着像整图缩了一半）。
  裁出来那块会**按匹配区的占比去要合适的解码尺寸**，所以是**完整放大**给你看，
  不会被画布切掉上下两截。
- **左边两个视图可切**：`相似分组` / `全部图片`。后者把所有扫到的图都列出来
  （含**没配上对的**），并按**质量从差到好**排，差的带徽章 + 琥珀色标题，
  直接就能看出哪几张该清理。徽章文字**跟着实际命中的判据走**：
  分辨率不够的写「低清」，尺寸够但压缩完只剩几 KB 的写「体积小」。
  在「全部图片」里点一张，右边立刻显示它并把它最像的拉来对比
  （左下的列表也跟着切成「与它相似」）；**一张相似对象都没有的图也能点** ——
  这时退化成**单图模式**：预览和信息卡照常显示它自己，右格收起来，不留半边空白。
  切回「相似分组」会回到你上次看的那一组。
- **删除 = 移动到扫描文件夹下的 `_隔离`**（见下）。
- **一键清理完全重复**：只认**字节 100% 相同**的（文件哈希一致），
  按文件大小先分组省掉 99% 的读盘时间；每组保留分辨率最高 / 文件最大的那张，
  其余移进隔离夹。删之前会把「保留谁、移走谁」列出来让你确认。
- 操作只剩**复制到剪贴板**这一类：复制 A / 复制 B（图片本体）、复制两个文件名、
  复制完整路径、定位。
  （早先版本还有一份「一键找高清」的 12 个国内站点清单 + 提示词 + 自动开网页，
  已按要求**整条删掉**。剪贴板被系统拒绝时会自动降级成「导出临时副本 + 定位」。）

**灵敏度** 三档，都是从同一份标定数据里来的（实测数据见下表，不是随手填的）：

| 档 | 闸门 | 强判据 相关/指纹 | 宽松判据 | 逐对命中/误报 | 分组：完整/被拆/跨图案污染 |
|---|---|---|---|---|---|
| 严格 | ≥0.70 | ≥0.93 / ≤18 | ≥0.90 / ≤22 | 166 / **0** | 1 / 7 / **0** |
| **标准**（推荐） | ≥0.60 | ≥0.93 / ≤18 | ≥0.86 / ≤22 | 175 / **0** | 2 / 6 / **0** |
| 宽松 | ≥0.60 | ≥0.90 / ≤20 | ≥0.80 / ≤24 | 189 / 5 | 0 / 6 / **2** |

> 「宽松」档会把两组不同图案并到一起（污染 2），这是它拿召回换来的代价。
> 「标准」档跨图案误报为 0，是默认值。

## 删除与隔离夹

**删除不是真删**，是把文件**移动**到扫描文件夹下的 `_隔离` 子目录：

```
扫描文件夹/
  照片.jpg
  _隔离/            ← 删掉的都进这里
    照片.jpg
    照片-1.jpg     ← 重名自动加序号，绝不覆盖
```

- **想还原**：把文件从 `_隔离` 拖回上层就是恢复。
- **扫描会自动跳过 `_隔离`**（`scan.iter_images` 里过滤掉了），
  所以删完再扫一遍，那些图不会又冒出来。
- 扫描源是「单独添加的图片」时，隔离夹建在它的**父目录**下；
  有多个扫描源、且它们互相嵌套时，取**最深**的那个（不会删到外层去）。
- 移动失败（跨盘、被占用）会退化成「复制 + 删源」，且**先复制成功再删**；
  两步都失败就原样不删并如实报错。隔离夹的顺序是**先扫、列清单、再动手**。

## 判定原理（为什么这么设计）

三级结构，每一级只干一件事：

```
① 闸门（颜色箱集合）
   把图量化成 12³=1728 个颜色箱，做成一个位图（一个大整数）。
   同源的两块裁剪，用到的颜色必然高度重叠 —— 几个位运算就能把
   绝大多数无关配对判掉。实测：同组召回 168/168，异组只留下 10%。

② 提议（区域指纹）
   把图归一到一个 64 长边的「工作网格」（保持长宽比）建积分图；
   在网格上撒一批候选区域（17 档长宽比 × 几档缩放 × 九宫格偏移），
   每个区域算一个 64 位 DCT 指纹。只在**同一长宽比档内**两两比。

③ 判定（像素级 Pearson 相关）
   取指纹最近的前 3 对候选，挑**相关最高**的那一对（不是指纹最近的
   那一对 —— 实测指纹最近的经常是假的），相关 ≥ 阈值才算数。
```

必须三级的原因：

- **只有哈希不行**：64 位指纹会偶然撞车（实测不同图案也能撞到距离 8）；
- **只有像素相关也不行**：平坦区域之间天然的相关系数就很高（实测不同图案的近线性区域能撞到 0.997），
  所以要排除面积过小（<15%）和对比度过低（标准差 <12）的区域；
- **哈希上限不是越紧越好**：裁剪不改变画面结构，相关系数常常是 `1.000`，
  真正拦住它们的是指纹距离。实测把上限从 10 放到 18，命中从 162 涨到 175，
  误报仍是 0；放到 20 才开始出现跨图案污染，所以停在 18。

**分组只用「强边」**（并查集有传递性，宽松边会把 A~B~C 串成 A~C ——
实测这么干会把 4 种图案串成一个 36 张的跨类大组）。宽松边不丢，
界面上做成「疑似对」跟真组并排放在同一个列表里，点开一样能对比。

## NIQE：无参考图像质量评价

「分辨率 / 体积」只能看出「小」和「压过头」，看不出「糊」。所以又接了一条
**NIQE**（Natural Image Quality Evaluator，Mittal / Soundararajan / Bovik，IEEE SPL 2013）——
不需要原图，靠「这块像素的统计离自然图像有多远」打分。纯标准库实现，在 `niqe.py`；
pristine 模型参数在 `niqe_model.py`（由 `make_niqe_model.py` 从官方 npz 生成）。

### 实现对不对：对着官方数值验

| | 分数 |
|---|---|
| 官方 MATLAB（论文作者实现） | 5.72957338 |
| BasicSR 记录的官方结果 | 5.7295763 |
| **本实现**（`testdata/baboon480.png`） | **5.7295739** |

偏差 5.04e-07，`test_niqe.py` 里这条断言卡的是 1e-4，实际小三个数量级。

光对上数还不够 —— 万一是「碰巧读了个常数回来」呢？所以还钉了**判别力**：
把模型的两个尺度互换、把 4 个方向的 AGGD 参数组互换，分数必须偏离
（实测偏离 0.06 ~ 2.18）。常数实现过不了这两条。

### 分数值不值得信：看块数

NIQE 要在图上切 96×96 的块，用这些块估一个 36 维分布。**块太少，估出来的分布
本身就是噪声** —— 这不是「不太准」，是没意义。拿 baboon（正好 5×5 = 25 块）
做自举，随机抽 k 个块重算分数（抽 40 次）：

| 用几个块 | 分数中位 | 最小 ~ 最大 | 相对极差 |
|---|---|---|---|
| 2 | 10.19 | 6.80 ~ 22.69 | **156%** |
| 4 | 8.69 | 6.33 ~ 13.29 | 80% |
| 9 | 6.84 | 5.79 ~ 8.59 | 41% |
| 12 | 6.34 | 5.58 ~ 8.18 | 41% |
| 16 | 6.17 | 5.45 ~ 7.27 | 30% |
| 20 | 5.91 | 5.54 ~ 6.58 | 18% |
| 25（全用） | 5.7296 | — | — |

**同一张图的同一批块，只改「用几个」**，2 个块时就能在 6.8 ~ 22.7 之间乱跳 ——
档位一口气从「自然」跳到「明显劣化」。所以界面上不给假档位：

| 块数 | 界面上写什么 |
|---|---|
| ≥ 16（`SOLID_BLOCKS`） | `清晰度 NIQE 5.73（自然）` —— 给档位 |
| 9 ~ 15 | `清晰度 NIQE 20.82（只 15 块，档位只作参考）` —— **不声称档位** |
| < 9（`MIN_BLOCKS`） | `清晰度 算不了 · 图太小（只能切出 2 个 96×96 的块，至少要 9 个）` |

> 16 这条线**是判断，不是定论** —— 上表的极差是拿 baboon（纹理花、块间差异大）
> 自举出来的最坏情况，平滑照片抖动会小些。理由和「换 12 或 20 也说得通」写在
> `niqe.py` 顶部，改那一个常数就行，别处都从它派生。

### 档位门槛是实测标定出来的

2 张基准图 × 11 种劣化 = 22 个样本，全部走真实管线（GDI+ 精确解码 → 长边压到 640 → NIQE）：

| 样本 | baboon 480×480（25 块） | 1/f 合成图 640×480（30 块） |
|---|---|---|
| 原图 | **5.73** 自然 | **6.39** 自然 |
| 高斯模糊 σ=0.6 | **3.16** 自然 ⚠️ | 6.38 自然 |
| 高斯模糊 σ=1.2 | 5.60 自然 | 6.66 轻微劣化 |
| 高斯模糊 σ=2.5 | 8.73 明显劣化 | 8.22 明显劣化 |
| 高斯模糊 σ=5.0 | 11.76 明显劣化 | 10.91 明显劣化 |
| JPEG q=30 | **3.16** 自然 ⚠️ | 6.59 轻微劣化 |
| JPEG q=15 | 4.56 自然 | 7.06 轻微劣化 |
| JPEG q=5 | 8.58 明显劣化 | 9.85 明显劣化 |
| 噪声 σ=15 | 7.96 轻微劣化 | 6.81 轻微劣化 |
| 压扁 4 倍 | 10.02 明显劣化 | 8.60 明显劣化 |
| 压扁 8 倍 | 23.86 明显劣化 | 16.65 明显劣化 |

`6.5 / 8.0` 就是把「和原图一个量级」「比原图明显更远」分开的位置。

> ⚠️ **NIQE 不是清晰度刻度尺。** 它对「轻微劣化」**不单调**：baboon 原图 5.73，
> 轻度模糊 σ=0.6 反而掉到 3.16、JPEG q=30 也掉到 3.16 —— 而同样的操作
> 在 1/f 图上几乎不动（6.39 → 6.38 / 6.59）。所以：
> ① 档位刻意**不叫「清晰 / 模糊」**，只说「自然 / 轻微劣化 / 明显劣化」；
> ② 信息卡上那句「NIQE 越低越自然（仅同组内可比）」是**必须**写的 ——
> 跨内容比较本来就在它的用法之外。

### 三条代价，说在前面

- **所有图都先压到长边 640 再算**（纯 Python：640 图约 0.7 s，960 图约 1.7 s）。
  好处是一批图横着比是公平的、耗时可控；代价是**轻微模糊会被缩小这一步抹掉一部分**，
  只剩「明显劣化」看得见。
- **算 NIQE 必须走 GDI+ 精确解码**（`winimg.load_pixels_exact`），**不能**用界面预览
  那条 Shell 缩略图路径 —— 实测同一张图 Shell 回的像素 **70% 的字节不同**
  （均值差 6.1、最大 101），分数会从 5.73 漂到 6.21。用了同源合成样本对照：
  精确解码 21.89 / 22.71，缩略图路径 17.31 / 17.85。
  GDI+ 解不开的格式（WEBP / HEIC）**如实说算不了**，绝不退回那条路凑一个数。
- **异步算 + 按 (路径, mtime) 缓存**，不卡界面；算完只改信息卡里那一段文字，
  并且要核对「这一侧还是当时那张图」，防止用户已经点走之后旧结果张冠李戴。

## 配色：白底 + 干净的天蓝强调 + 对比度验算

这套配色被用户**连着提了五次**（「有些灰，喜欢蓝色系」→「换浅天蓝」→
「浅一些、亮一些、通透一些」→「**颜色灰不溜秋的好恶心**，开始扫描的按键为什么不改」→
「**这个颜色太重了，还有背景的蓝色改回白色**」）。
改了五轮才走到现在这套，中间两次把方向搞反了，全记录在下面。

**最终定稿（第五轮）**：页面底**纯白**（`PAGE=#ffffff`），强调色是更轻一档的
天蓝 `#7cc8f1`（色相 201°、彩度 117、与白底 1.84），深字压在上面 8.2。
层次不再靠底色反差，**全靠描边 + 阴影**。

`test_ui.py::test_palette` 把每一组前景/背景按 WCAG 公式算了一遍
（`(L1+0.05)/(L2+0.05)`，L 先做 gamma 反变换）：

| 用途 | 色对 | 对比度 | 要求 |
|---|---|---|---|
| 正文 | `#193752` on `#ffffff` | 12.28 | ≥ 7.0 |
| 次要字 | `#2b6395` on `#ffffff` | 6.32 | ≥ 4.5 |
| 提示字 | `#4a83a9` on `#ffffff` | 4.11 | ≥ 3.5 |
| **CTA 深字压亮底** | `#08283f` on `#7cc8f1` | 8.22 | ≥ 4.5 |
| 低质量强调 | `#a9723c` on `#ffffff` | 4.07 | ≥ 3.5 |

仍带**白字**的按钮只剩 `teal` / `danger` 两类（界面上目前只有 `danger` 在用，
即「删除」）。白字按钮的渐变**只能往暗里做**（早先 hover「变亮」，白字掉到 2.59）：

| 按钮 / 状态 | 上渐白字 | 下渐白字 |
|---|---|---|
| teal（次要实心） | 4.13 / 4.55 / 6.60 | 4.55 / 5.43 / 8.35 |
| danger（删除） | 4.05 / 4.42 / 6.79 | 4.42 / 5.27 / 8.61 |

（要求 ≥ 4.0。）`_spec()` 不写死十六进制，全部从 `Palette` 推导 —— 改主色整块跟着变。

`primary` CTA 三态实测（都是深字，不存在白字问题）：
字压底 8.92/8.22 → 8.22/6.94 → 7.39/6.64，底与白底 1.70/1.84 → 1.84/2.18 → 2.05/2.28。

### ⚠️ 坑一：把「浅」做成了「去饱和」，结果是一整屏灰白

用户说「灰不溜秋」那次，我量了一下**彩度**（最大通道 − 最小通道，纯白是 0）：

| | 当时 | 现在 |
|---|---|---|
| 页面底 | `#eaf7ff` 彩度 **21** | `#ffffff` 纯白（**主人第五轮定的**，故意的） |
| 选中行 | `#e4f4fe` 彩度 26 | `#c4e4fc` 彩度 56 |
| 描边 | `#dceefc` 彩度 32 | `#aed7f7` 彩度 73 |

**当时的页面底彩度只有 21 —— 蓝色被我洗没了，看着当然是一片灰白**，
而所有对比度断言都还是「合格」的。教训：**「浅」≠「淡到没颜色」；
清新通透 = 颜色干净 + 亮度高，不是把饱和度抽干**。所以测试里加了**彩度下限**
（选中行 ≥ 45、描边 ≥ 55……），下次再被洗灰会当场测出来。
页面底则是反向的一条：**必须是纯白**（主人原话「背景的蓝色改回白色」），
防它悄悄蓝回去。

### ⚠️ 坑二：主色的「白字天花板」，最后是靠**换形态**破的

主色原本是「实心深蓝 + 白字」。白字必须 ≥ 4.0，于是主色被**钉死**在中深蓝：

| 主色 | 本色 | 上渐白字 | |
|---|---|---|---|
| `#0d78b8` | 4.78 | 4.32 | 上一版 |
| `#1179bd` | 4.67 | 4.23 | 还能用 |
| `#127dc2` | 4.43 | 4.06 | 贴线 |
| `#1380c4` | 4.27 | **3.92** | 白字开始看不清 |

**主色最多只能亮 5% 左右** —— 那支蓝怎么看都闷，这就是用户问
「开始扫描的按键为什么不改」的原因。第三轮我还在「其他地方」挣富余、
把主色留着不动，第四轮才把它**换形态**：

> **「开始扫描」= 亮天蓝底 + 深字 `#08283f`**。
> 白字约束**根本不存在了**（第四轮底色是 `#4fb6ec`，与白底 2.27；
> 第五轮主人说「这个颜色太重了」，再提亮到 `#7cc8f1`，与白底 1.84，靠深描边守边界）；
> 而且深字压亮底的对比度有 **8.2 ~ 8.9**，比白字方案的 4.2~4.7 **好读得多**。
> 三态（normal / hover / press）深字 8.9 → 8.2 → 7.4。

结果：主行动按钮从「一屏最深的色块」变成「一屏最**鲜艳**的色块」——
这正是「清新」该有的样子。那条旧断言「主色 on 卡片 ≥ 4.5」也随之作废
（亮底跟白底比 4.5 毫无意义），换成真正的要求 **「CTA 深字压亮底 ≥ 4.5」**，
外加一条**源码扫描**守着「`PRIMARY` 只做填充、从不作文字色」这个前提。

### 选中态（`on`）：也要浅，但**必须看得出来选了谁**

顶栏有四处「分段控件/开关」：`含子文件夹`、灵敏度三档、`相似分组 / 全部图片`、
`只看匹配区域`。早先「选中的那个」直接用 `primary`（实心深蓝 + 白字）——
一屏四个实心深块，就是那句「**已选中的按钮颜色同理**」要解决的问题。

现在的 `on` = **浅天蓝底 + 深蓝描边 + 深字**，三态全浅（主色提到 `#7cc8f1` 后，
混白比例也从 0.46 降到 0.34/0.26/0.18，不然选中底跟白底只剩 1.37 贴线）：

| 要求 | 实测 | 为什么 |
|---|---|---|
| 底要**真的浅** | 与白底 1.50 ~ 1.74 | 这是改动的目的 |
| 跟**未选中分得开** | 选中底与未选中底（白）1.50 起 | 不然用户看不出哪个是开着的 |
| **字**压底 ≥ 4.5 | 8.20 / 7.83（normal 上/下） | 字色用 `TEXT` |
| **描边**压底 ≥ 2.8 | 3.98 / 4.09 / 4.54（三态） | 描边是「选中」的第二重信号 |

两条踩过的坑，都写死在测试里了：

- **字色不能用 `PRIMARY_D`**（别的按钮都用它）。深蓝字压在浅底上实测只有
  **3.7 ~ 4.4**，不到 4.5 —— 换 `TEXT` 立刻 6.9。别为了「看起来统一」改回去。
- **描边要跟着底逐态加深**。hover/press 时底色加深，同一支描边压上去会掉
  （曾实测到 2.51 / 2.21）—— 三态分别用 `PRIMARY_D` 混白 4% / 本色 / 混黑 10%。

另外，测试对「选中」的断言**不是「它不是 ghost」**，而是三件事一起：
选中的那个是 `on`、**其余的都必须退回 `ghost`**（互斥）、关掉开关要退回未选中。
只断言「不是 ghost」的话，「三个按钮全都亮着」也能过，但用户根本看不出选的是哪个。

### 「是天蓝、不是靛蓝」要看**色相**，不能只看蓝通道

**靛蓝和天蓝都是「B 通道最大」**，光看蓝通道分不出差别 —— 差别在**色相**：

| | 主色 | 色相 | |
|---|---|---|---|
| 第一版（被否） | `#3b74c6` | **215.4°**（偏紫的靛蓝） | 「不够天蓝」 |
| 现在 | `#7cc8f1` | **201.0°**（天蓝） | |

所以测试里除了「关键色都是蓝调（B 通道最大）」，还量了**色相必须落在
195~212°**（主色收紧到 198~208°）—— 少这一条，下次又会被顺手改回靛蓝而测不出来。
（页面底是例外：它现在是**故意**的纯白，由「PAGE 必须是 #ffffff」这条断言守着。）

### 预览区占比：结论条压一行，抠出来的高度全给图

第五轮主人还反馈「**哪怕是全屏，预览区的占比还是太小**」。对比图是竖图时
显示大小完全由**画布高度**决定（宽度大把剩余），所以唯一有效的手段是
**从别的区域抠高度**：

| 改动 | 效果 |
|---|---|
| 结论条两行 → **一行**（pill + 结论 + 副说明同行） | 105px → 69px |
| 顶栏 pad 10→8、进度行 pady 9→6 | −8px |
| 信息卡/操作卡 pad 9→7、间距 8→6 | −8px |
| 对比卡 pad 10→6、图注行距 6→4、外框 pady 12→10 | −10px |

画布高度 **749 → 852**（窗口 1410 时占比 **53.1% → 60.4%**），
1328×2048 的竖图 fit 缩放从 35.9% 提到 40.8%，**显示高度多出 14%**。
这条用探针量化验收过（建窗口量 `winfo_height`），不靠目测。

改色前先跑 `calib_palette.py`（**不建窗口**，只算数）：它把候选配色按上面**全部**硬指标
过一遍，并记着试过但没过的方案（各自栽在哪一条），省得重试第二遍。

## 界面清晰度：进程 DPI 感知

界面「糊」的根因不是渲染质量，而是**进程没有 DPI 感知**：Windows 会把整个窗口的
位图按缩放比拉伸，字先按 96 DPI 渲染成 13px，再被插值放大到 19.5px —— 边缘全是糊的。
实测（150% 屏）：

| | 开感知前 | 开感知后 |
|---|---|---|
| Tk 认为 1 英寸 | 95.9 px | 143.9 px |
| `winfo_screenwidth` | 1707 | **2560** |
| 10pt 雅黑字高 | 13 px（再被系统拉成 19.5px） | **27 px**（直接渲染） |

所以程序在**创建窗口之前**调 `SetProcessDpiAwarenessContext(-4)`（失败退
`SetProcessDpiAwareness(2)`，再退 `SetProcessDPIAware`），并把
**所有写死的像素值过一遍 `uikit.sc()`**（`dpi/96` 倍）—— 字不用管，
用的是「点」，Tk 按 `tk scaling` 自己换算。`test_ui.py` 里有一条断言专门盯这个：
Tk 报的 DPI 必须等于系统真实 DPI。

## 已知限制（实话）

- **同场景不同构图只有约一半能认出来**。这类图（连拍、换角度）在像素上本来就不同，
  只能靠「宽松判据」捞一部分；把直方图单独当判据也不行（实测正例最小 0.059 < 反例最大 0.610）。
  所以它们统一标成「疑似」，不当成确定结论。
- **徽章（那两条「质量差」判据）只按能确定的东西判**，而且**标签如实说明是哪条命中的**：
  长边 < 480 或不足 0.2 MP → 「低清」；尺寸够大（长边 ≥ 480）但文件 < 20 KB
  → 「体积小」（分辨率不低，是压缩后几乎没信息量）；长边 < 1024 或不足 0.8 MP
  → 「一般」。
  之所以分两个标签：一条 560×380 / 9 KB 的图写「低清」是撒谎（它分辨率并不低），
  而徽章写死一个词还会跟副标题里的标签自相矛盾。
  副作用：纯色 / 扁平设计图天生压得极小，也可能被标「体积小」——
  徽章只是**提醒**，它不会自动删任何东西，删不删由你点。
- **NIQE 目前只出现在信息卡里，不进徽章、也不参与排序**，三条理由：
  ① 它是**异步**算的（0.7 s/张），列表早就画完了分数才到，排序会在用户眼皮底下变；
  ② 一个目录上百张图若都要分数，光算就要一两分钟；
  ③ 少于 16 块时它连档位都不该给（见上），拿它自动标「差」会误伤小图/裁剪图。
  所以它被定位成「选中某张时，给一个额外的客观参考」，而不是自动判据。
- **NIQE 只对「明显劣化」敏感**：轻微模糊、轻度压缩它可能不动甚至更低
  （见上表 σ=0.6 与 q=30 那两行）。真正「有点糊但分辨率够大、文件也正常」的图，
  它也只能在明显劣化时才给得出信号。
- **「完全重复」只认字节 100% 相同**（文件哈希一致）。同一张图另存成别的格式、
  或重新压缩过的，一律**不算**重复 —— 宁可少删，不可误删。
  字节相同时「保留哪张」的并列判据是：像素最多 → 文件最大 → 修改时间最新 → 路径最短。
- **渐变/纯色类图案**的指纹不稳，召回明显低于有明确纹理的图案。
- 「被拆」的那几组：同一图案的多张图没能全连成一个组（标准档完整 2/8、被拆 6）。
  漏掉的边并没有进「未匹配」，只是没连成完全图 —— 点开组里的图仍能看到与代表图的相似度。
- 界面预览/指纹走的是 **系统缩略图管线**，所以能认哪些格式取决于系统装了哪些解码器
  （HEIC/AVIF 需要系统有对应扩展）。认不出的图会算作「解码失败」跳过。
  另外注意：**Shell 缩略图路径返回的不是原图** —— 实测同一张 PNG 请求 480/512/1024/2048
  尺寸时像素有 70% 的字节跟原图不同（均值差 6.1），只有某些尺寸恰好精确。
  所以 NIQE 走的是另一条 **GDI+ 精确解码**（`load_pixels_exact`，实测与 Pillow 逐字节相同），
  但 GDI+ **不支持 WEBP / HEIC / AVIF** —— 这些格式的图会「算不了清晰度」，如实说，不编。
- 真实分辨率解析支持 PNG/JPEG/GIF/BMP/WebP/TIFF；HEIC/AVIF 只能靠扩展名显示格式，尺寸显示「解析不了」。
- 内存与时间：比较是 O(n²)，但闸门会挡掉约 90%。实测 59 张 → 1711 对约 3 秒（含首次解码）。
  上万张的量级需要先按目录分批扫。
- 移动是**不可逆地在磁盘上换位置**（虽然没删）。程序只管移到 `_隔离`，
  **不会**自动清空隔离夹 —— 确认没问题后请自己删那个文件夹。
